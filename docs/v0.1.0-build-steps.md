# pouch nRF54L15 Build Runbook

This document records the Windows build steps used while bringing up `pouch` on `xiao_nrf54l15`.

Two states were tested:
- `pouch` release `v0.1.0` (`73662de`) with NCS `v3.0.1`
- latest upstream `pouch` (`origin/main`, tested at `d161705`) with NCS `v3.2.3`

The XIAO nRF54L15 board is available in the newer NCS `v3.2.3` stack, not in the older `v3.0.1` stack used by `pouch` `v0.1.0`.

## 1) Set `pouch` to the release commit

From `C:/ncs_pouch_soil/pouch`:

```powershell
git checkout 73662de
git show -s --oneline --decorate HEAD
```

Expected result includes:

```text
73662de (HEAD, tag: v0.1.0) ...
```

## 2) Build attempt and initial failure

From `C:/ncs_pouch_soil/pouch/examples/ble_gatt`:

```powershell
west build -b nrf52840dk/nrf52840 --pristine
```

This initially failed due to NCS revision mismatch and tooling issues.

## 3) Align NCS workspace revisions

From workspace root `C:/ncs_pouch_soil`:

```powershell
west update
```

Why: `nrf` was at `v3.0.1` while some imported projects (such as `zephyr`/`mcuboot`) were still at newer revisions. Aligning all projects removed Kconfig/toolchain incompatibilities from mixed versions.

## 4) Install required Python dependencies

From `C:/ncs_pouch_soil/pouch`:

```powershell
python -m pip install -r requirements.txt
python -m pip install cryptography
```

Why:
- `zcbor` (from `requirements.txt`) is required for code generation during build.
- `cryptography` is required by MCUboot `imgtool.py` for image signing.

## 5) Force the NCS-managed Zephyr SDK

Set environment variable before building:

```powershell
$env:ZEPHYR_SDK_INSTALL_DIR = "C:/ncs/toolchains/66cdf9b75e/opt/zephyr-sdk"
```

Why: build failures were seen when using a different host-installed SDK (`C:/Users/Brian/zephyr-sdk-0.17.2`). For this workspace, using the NCS-managed SDK resolved ABI/header/toolchain mismatches.

## 6) Successful build

From `C:/ncs_pouch_soil/pouch/examples/ble_gatt`:

```powershell
west build -b nrf52840dk/nrf52840 --pristine
```

Build completed successfully and generated:

- `build/ble_gatt/zephyr/zephyr.elf`
- `build/dfu_application.zip`
- `build/merged.hex`

## 7) Test with `xiao_nrf54l15`

Attempted command:

```powershell
west build -b xiao_nrf54l15/nrf54l15/cpuapp --pristine
```

Result in this workspace:
- Failed at configure time with `No board named 'xiao_nrf54l15' found.`
- This indicates that board definition is not currently present in the active Zephyr/NCS board set.

Quick checks:

```powershell
west boards | Select-String xiao
west boards | Select-String nrf54l15
```

In this environment, `nrf54l15dk/nrf54l15/cpuapp` is available, but `xiao_nrf54l15/...` is not.

## 8) Update to latest `pouch`

Latest upstream `pouch` was tested on a branch based on `origin/main`:

```powershell
git fetch origin
git switch -c latest-pouch-test origin/main
```

The latest `west-ncs.yml` targets NCS `v3.2.3`:

```yaml
nrf:
  revision: v3.2.3
```

From workspace root `C:/ncs_pouch_soil`:

```powershell
west update
```

After updating, the XIAO board is present:

```powershell
west boards | Select-String xiao_nrf54l15
```

Expected result:

```text
xiao_nrf54l15
```

## 9) XIAO app-only build

The app-only build succeeds:

```powershell
$env:ZEPHYR_SDK_INSTALL_DIR = "C:/ncs/toolchains/66cdf9b75e/opt/zephyr-sdk"
$env:Path = "C:/Users/Brian/AppData/Local/Programs/Python/Python312/Scripts;$env:Path"
west build -b xiao_nrf54l15/nrf54l15/cpuapp --pristine --no-sysbuild
```

Successful output included:

```text
Memory region         Used Size  Region Size  %age Used
           FLASH:      332172 B      1428 KB     22.72%
             RAM:       68312 B       188 KB     35.48%
Generating files from .../build/zephyr/zephyr.elf for board: xiao_nrf54l15
```

## 10) XIAO sysbuild/MCUboot failure

The default sysbuild command recognizes the board, but fails while building MCUboot:

```powershell
west build -b xiao_nrf54l15/nrf54l15/cpuapp --pristine
```

Failure:

```text
C:/ncs_pouch_soil/bootloader/mcuboot/boot/zephyr/flash_map_extended.c:70:2:
error: #error "FLASH_DEVICE_ID could not be determined"
```

This means MCUboot could not determine the flash device that contains the boot slots for this board configuration. The application itself builds, so the issue is specifically the sysbuild/MCUboot flash and partition metadata for `xiao_nrf54l15`.

Until that flash metadata is fixed, use `--no-sysbuild` for direct app flashing and development. MCUboot is still needed later if the goal is bootloader-managed updates such as signed DFU/OTA images.

## Repeatable helper script

To build the XIAO app-only image without re-running setup manually, use:

```powershell
scripts/build_ble_gatt_v010.ps1
```

Script location:

- `scripts/build_ble_gatt_v010.ps1`

Optional usage:

```powershell
scripts/build_ble_gatt_v010.ps1 -SkipWestUpdate
```

Use `-SkipWestUpdate` only when the workspace is already aligned.

Build for another board:

```powershell
scripts/build_ble_gatt_v010.ps1 -Board "nrf54l15dk/nrf54l15/cpuapp"
```

Try the sysbuild/MCUboot path:

```powershell
scripts/build_ble_gatt_v010.ps1 -UseSysbuild
```

At the time of testing, `-UseSysbuild` fails for `xiao_nrf54l15` with the MCUboot `FLASH_DEVICE_ID could not be determined` error described above.
